## 4. Row Classification & PUC Hierarchy Mechanics

The historical trial balance report presents data in a hierarchical tree structure flattened into worksheet rows. Understanding how summary rows and detail rows are formatted is critical for correct comparison.

### 4.1 PUC Hierarchy Level Classification
In Colombian accounting (Decreto 2650 de 1993 / NIIF SME adaptations), account codes follow a strict length-based hierarchy:

| Level | Name | Code Length | Example Code | Is Leaf / Third-Party Row? | Role in Verification |
|:---:|:---|:---:|:---:|:---:|:---|
| **1** | Clase | 1 digit | `1` (Activo) | No (Summary Node) | Macro rollup verification |
| **2** | Grupo | 2 digits | `11` (Disponible) | No (Summary Node) | Group rollup verification |
| **3** | Cuenta | 4 digits | `1105` (Caja) | No (Summary Node) | Standard account rollup verification |
| **4** | Subcuenta | 6 digits | `110505` (Caja General) | No (Summary Node) | Subaccount rollup verification |
| **5** | Auxiliar | 8+ digits | `11050501` (Caja General Principal) | Yes (Detail Node) | Leaf account baseline |
| **-** | Tercero | Nested under 8+ digits | NIT / Doc in Col 3 | Yes (Third-Party Detail) | **Third-party granular benchmark** |

### 4.2 Distinguishing Summary Rows vs Detail Third-Party Rows
When parsing a row from the benchmark sheet:

1. **Header & Title Rows**: Rows before the detected table header row, or rows containing report title strings. -> **SKIP**.
2. **Subtotal & Grand Total Control Rows**: Rows where Col 1 or Col 2 contains `"TOTAL"`, `"GRAND TOTAL"`, `"SUBTOTAL"`, `"SUMAS IGUALES"`, `"VAN"`, `"VIENEN"`. -> **PARSE AS CONTROL TOTALS** for global debits = credits check.
3. **PUC Parent Summary Rows**: Rows where `account_code` length is 1, 2, 4, or 6 digits, and `third_party_doc` is empty or matches the account code. 
   - *Behavior*: These rows represent pre-aggregated parent totals. The comparison engine can either compare these against generated PUC rollups directly or calculate rollups dynamically from detail rows.
4. **Third-Party Detail Rows**: Rows where `third_party_doc` is populated (e.g. NIT `900123456-1`), or where `account_code` is 8+ digits long.
   - *Behavior*: These constitute the fundamental leaf entries for `compareTrialBalances()`.

## 5. Numeric Formatting, Currency & Sign Conventions

### 5.1 ExcelJS Cell Value Normalization
Excel files may contain numbers as pure numeric floats, formatted currency strings (e.g. `"$ 45.000.000,00"` or `"($ 1.500.000,00)"`), or formula cells (`{ formula: 'SUM(...)', result: 45000000 }`).

The numeric parser must handle all representations cleanly:
```typescript
function parseNumericCell(val: any): number {
  if (val === null || val === undefined) return 0;
  if (typeof val === 'number') {
    if (isNaN(val)) return 0;
    return Math.round((val + Number.EPSILON) * 100) / 100;
  }
  let str = getCellValueString(val);
  // Handle ($ 1.500,00) or negative signs
  let isNegative = false;
  if (str.includes('(') && str.includes(')')) {
    isNegative = true;
    str = str.replace(/[()]/g, '');
  } else if (str.startsWith('-')) {
    isNegative = true;
    str = str.substring(1);
  }
  // Sanitize non-numeric currency characters
  str = str.replace(/[$]/g, '').replace(/\u00A0/g, ' ').trim();
  // Standardize thousand dots and decimal commas
  // ...
  let num = parseFloat(str);
  if (isNaN(num)) return 0;
  return isNegative ? -Math.abs(num) : num;
}
```

### 5.2 Balance Identity & Sign Mechanics
In trial balance reports:
- `Saldo Final` formula identity: 
  $$\text{Saldo Final} = \text{Saldo Inicial} + \text{Débitos} - \text{Créditos}$$
  *(For Asset, Expense, Cost accounts - Classes 1, 5, 6, 7)*
  
  $$\text{Saldo Final} = \text{Saldo Inicial} + \text{Créditos} - \text{Débitos}$$
  *(For Liability, Equity, Revenue accounts - Classes 2, 3, 4)*

- **Float Tolerance Requirement**: All financial balance comparisons must use strict COP rounding (`Math.round(val * 100) / 100`) with tolerance:
  $$\left| \text{Balance}_{\text{generated}} - \text{Balance}_{\text{historical}} \right| \le 0.01\text{ COP}$$

## 6. Proposed TypeScript Parsing Strategy for `trial-balance-comparator.ts`

### 6.1 Interface Contracts
```typescript
export interface BenchmarkTrialBalanceRow {
  accountCode: string;
  accountName: string;
  thirdPartyDoc: string;
  thirdPartyName: string;
  initialBalance: number;
  debit: number;
  credit: number;
  finalBalance: number;
  pucLevel: 1 | 2 | 3 | 4 | 5;
  isSummaryRow: boolean;
}

export interface ParsedBenchmarkReport {
  filePath: string;
  fiscalYear: number;
  period: string;
  rows: BenchmarkTrialBalanceRow[];
  totalDebit: number;
  totalCredit: number;
  isControlBalanced: boolean;
}
```

### 6.2 Step-by-Step Parsing Workflow
1. **Read-Only Buffer Wrapping**: Wrap Excel loading inside `withReadOnlyGuard(filePath, async (buffer) => ...)` to ensure no filesystem writes.
2. **Worksheet Selection**: Access `workbook.worksheets[0]` (or active worksheet).
3. **Dynamic Header Detection**: Scan rows 1 through 25 using normalized string matching for keywords: `codigo`, `cuenta`, `tercero`, `nit`, `identificacion`, `saldo inicial`, `debito`, `credito`, `saldo final`.
4. **Row Iteration & Normalization**:
   - Extract raw text values.
   - Identify header row and map column indices.
   - Filter empty rows and title header rows.
   - Classify row as summary or detail based on code digit length and presence of third-party document.
   - Clean up third-party NIT (fallback to `'0'` / `'CUANTIAS MENORES'` if unassigned).
5. **Control Total Assertion**: Verify total debits equal total credits within $\le 0.01$ COP tolerance.
